# 静档境内环境与数据恢复准备

更新：2026-11-02。部署设计和演练步骤，未购买服务器、未运行 Docker、未应用真实数据库迁移。沿用 [现有部署说明](deploy-mainland.md)，不重建数据协议。

## 最小架构与可见数据

原生 Flutter → HTTPS 网关 → Supabase Auth / PostgreSQL / 私有 Storage / Realtime / delete-account 函数。正文和附件在客户端加密，搜索在已解锁设备完成；服务器没有档案解密入口。服务器仍能见到账号、对象 ID、修订号、密文大小和请求信息。

先采用一台可维护的境内主机承载官方自托管栈，备份放在独立受控位置。数据库、Studio 和内部服务不公开；不要把 Supabase CLI 开发栈直接暴露公网。网关只提供必要 HTTPS API，管理访问另受限。解析域名、TLS、服务商与备案均待实际选择，未填写虚假域名。

[Supabase 官方自托管说明](https://supabase.com/docs/guides/self-hosting/docker)本轮列出完整栈最低 2 核、4 GB RAM、40 GB SSD，推荐更高；这些是上游基础条件，不是本项目容量保证。默认未含 Logs & Analytics，不为本项目默认加装记录请求正文的分析平台。正式版本须锁定实际 Docker 配置、镜像版本和变更记录；不直接跟随 main 自动升级。

本机没有 Docker 命令、没有已授权的正式主机；不安装新的系统软件或执行官方安装脚本，不把这份设计称为已部署。已有免费新加坡测试项目继续只用虚构记录。

## 增长检查：先测量再优化

已查源码：

- records 主键为 `(owner_id,id)`，查询按 owner_id 和 id，每页 500；账号隔离与索引已有基础，不新增重复索引。
- 客户端前台每 30 秒及变更/恢复前台对账，当前会拉取全部记录，未实现增量游标；列表 20 条只是渲染分批，搜索在本机全部已解锁记录中进行。
- SQLite 保存密文、待同步队列与冲突。record_mutations 为幂等重试保留响应，编辑次数会影响服务端增长。无引用附件暂保留到账号删除；不能为节约空间直接清除历史响应或附件，破坏重试/离线安全。
- 原声 WAV 为 44.1 kHz、单声道、16 bit；满两分钟约 10.1 MiB。原件是首要容量来源，不能把存储增长都归咎于文本。

本轮现有合成测试在本机搜索 1,000 篇约 250 字符的记录耗时 223 ms；这是单次测试诊断，不是 Redmi/iPhone 的内存、耗电或延迟验收。未读取本人内容或将真实档案上传作压测。

正式环境前用合成账号测量：记录与附件/幂等表大小、每次全量拉取字节与耗时、活跃前台设备数、每分钟请求、附件出入流量、内存和重试率。只记录数值与随机合成标识，不记录正文、原始文件名、口令或完整请求负载。

规划示例而非实际用量：100 用户每月各存 4 段满两分钟原声，新增原始音频约 3.94 GiB，尚未加副本和备份；若每个用户有 100 条、每条平均密文 4 KiB，前台每天 10 分钟、每月 30 天、每 30 秒全量拉取，仅这部分约 22.9 GiB/月，不含变更触发和附件。按真实测量更新，不据此承诺 900 元能覆盖服务。

## 生产数据和备份必须一起恢复

拟定目标供本人审阅：上线前三个月每日一致性备份，至少每月一次隔离恢复；目标 RPO 24 小时、RTO 1 个工作日，仅在演练通过并有维护资源后才能对外承诺。备份实际周期、保留天数、成本与删除窗口待确定。

一致性备份范围包含 Auth 用户/账号映射、vaults、records、record_mutations、account_deletions、私有对象存储原件、迁移和函数版本，以及必要服务配置的独立安全副本。业务密文不等于全部备份都不敏感：Auth 邮箱和运维凭据需要额外访问保护；服务端配置备份不能放进客户端包或源仓库。

对象存储与 PostgreSQL 需同一恢复点或可核对的对象清单。不能仅导出数据库后声称附件备份完成，也不能只备对象而丢失原账号 UUID。禁止读取客户端档案主密钥来“帮助恢复”。

隔离恢复演练：

1. 在全新非生产栈恢复账号/映射、数据库与对象快照，核对迁移/函数版本及访问策略；不连接生产客户端，不覆盖现有栈。
2. 用合成账号验证 OTP、口令/恢复密钥、附件解密、离线补传、重复提交及跨账号拒绝。核对 Auth ID、密钥封装和附件引用一致。
3. 重放恢复点之后已生效的账号删除/撤销记录，核对旧令牌和账号不能因恢复重新获得访问；未设计好这一流程不公开承诺删除完成。
4. 中断任一步保持旧服务及本机资料不变。验证通过后才准备有明确切换点、回退点、停写窗口和本人批准的正式变更。

本轮原生 libsodium、完整备份预检、独立离线解密、PGlite 权限和删除函数的本机测试已通过；它们不是服务器灾难恢复演练。服务器演练因没有隔离栈未执行，不虚构 RPO/RTO 达成。

## 升级与故障处理

每次更新先备份已验证的配置、数据库及对象清单，在合成环境验证旧客户端遇到新版本时保留原密文并提示升级。只有确定需要改变格式才写迁移，不无故升级加密协议。

客户端暂时断网：保留 SQLite、WAL、待同步队列和冲突，显示本机保存及等待连接状态；不删除后重拉。数据库打不开：先停止对该库写入，保留原文件/WAL 和错误类型，准备只读诊断及隔离副本验证，禁止以空库替换损坏库。现有代码没有完成通用 SQLite 修复器，不声称已具备自动修复任何损坏的能力。

服务器故障：先区分认证/邮件、网关、数据库、对象或 Realtime；检查状态码和脱敏指标。不在日志中倾倒正文或密钥，不以关闭 RLS、开放数据库、改成明文或删除数据快速“修好”。邮件故障和配额耗尽不应触发重复验证码风暴或收费升级。

发布采用人工确认后的版本化变更，不自动推送源码来绕过商店审核。原安装包与数据库备份各自保存，回退应用也需确认其能读取已经写入的数据格式，不能简单用旧包覆盖新格式。
